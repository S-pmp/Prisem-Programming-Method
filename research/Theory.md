# なぜTheoryが必要だったのか

PMPは当初、

Parts
↓
Model
↓
Coreおよび10 Actionによって構築されたソフトウェアアーキテクチャとして設計された。
しかし設計後、AI、セキュリティ、データベース、認証、API、権限管理、OSなどを観察していく過程で、一つの疑問が発生した。
それは、「なぜPMPはその構造になったのか」という問いである。本資料はPMPそのものではなく、「なぜその構造が生まれたのか」
を説明するための理論的整理である。

---

# 仮説1：PMPは情報構造である

従来のプログラミングは、ソフトウェアをコードの集合として扱う。つまり、コード→プログラムとして考える。
しかしAIの発展によって、コード生成そのものは自動化され始めている。同じ機能は、PHP、Java、Python、Go、AI生成コード
など異なる実装で表現できる。その場合、本質的な価値はコードではなく、その背後に存在する情報構造にあるのではないか。
PMPは、プログラミングを「コードを書く行為」ではなく、「情報構造を設計する行為」として再定義する試みである。

---

# 仮説2：Semantics → Grammar → Execution

PMPは次の3層を分離する。

Semantics
↓
Grammar
↓
Execution


## Semantics

意味。

システムが本来表現したい内容。

例：顧客　注文　攻撃　購入　会員

## Grammar

文法。

意味を構造として表現する方法。

例：query　save　update　delete　render

---

## Execution

実行。

実際に動作する部分。

例：PHP　Java　Python　Linux　MySQL ...

---

同じ意味は異なる文法で表現できる。

同じ文法は異なる実行環境で実現できる。

# 仮説4：多くの場合、攻撃の最終目的はコードそのものではなく、その先に存在する価値である可能性がある。

PMPを考察する過程で、次の観察結果が得られた。多くの攻撃者は、コードそのものよりも、その先に存在する価値を狙う。

例：顧客情報 個人情報 認証情報 決済情報 機密設計情報

つまり、攻撃→コード取得ではなく、攻撃→価値取得が本質である可能性がある。
そのため、価値へ到達する経路の設計が重要になる。

---

# 仮説5：Authorityは構造上の攻撃面の一部になり得る

既存のセキュリティは脆弱性へ注目する。
しかし別の見方もできる。
権限そのものが攻撃面になっている可能性がある。

例えば　Root権限　管理者権限　DB権限　クラウド権限など。
権限が増加すると、

Authority
↓
Access Scope
↓
Complexity
↓
Monitoring
↓
Operational Cost

という連鎖が発生する。

# 仮説6：監視は複雑性の症状である

監視は重要である。しかし、別の見方をすると、監視が必要になる理由そのものを観察できる。
例えば、

監視
↓
異常発見

ではなく、


なぜそこまで監視が必要なのかという視点である。

---

複雑な結合

大量の権限

多数の例外

依存関係

これらが増えるほど、監視も増える。そのため、監視の増加は複雑性の症状である可能性がある。

---

# 仮説7：RouteとMeaningの分離

システムは価値に到達するための経路を持つ。

PMPは、MeaningとExecutionを分離し、制御されたRouteで接続することを目指す。

---

経路が制御されることで、

- 結合増加
- 権限増加
- 依存関係増加

を抑制できる可能性がある。

---

# 仮説8：価値集中の原理

Root権限

DB

認証

OAuth

監視

Linux

などを観察した結果、一つの共通した疑問が生まれた。

なぜ価値は一箇所へ集中するのか？

既存システムでは、情報　権限　責任　監視　認証が同じ場所へ集中しやすい。その結果、単一障害点が発生する。
PMPは、価値そのものではなく、価値へ到達する仕組みを分離することで、価値集中を緩和できる可能性がある。
